Bookkeeping · PR #158 · producer-first

Give the detector something true to check.

PR #151 could see that a page asserted mutable state without a date. It could never say which belief was current. That answer has to be written, not inferred — so this builds the writers first.

426 tests · 37/37 mutations killed Green on Python 3.11 and 3.12. Four rounds of cross-model adversarial review (codex-cli, gpt-5.4), scoring 3 → 4 → 5. Three findings held unfixed and documented rather than closed.

A detector cannot decide what is true. Only a producer can.

What #151 proved

Stale updated dates and undated mutable claims are mechanically visible. 96 findings across 91 entities, all warnings.

What it could not

Whether a newer claim supersedes an older one. No amount of regex over present-tense prose answers that — it is a decision somebody made, not a property of the text.

The sequencing rule

Requiring the fields before any writer emits them would have produced compliance theater: a schema whose guarantees nothing supplies.

Four fields, four different provenance rules

FieldClockWho may write it
recorded_atSystem time — when the graph recorded this statepromote, mechanically. Never operator-supplied.
valid_fromClaim-effective time — when the claim became trueOnly a source or revision that supplies it. One metadata key, no fuzzy aliasing.
supersedes—revise / merge only.
revision_link—revise / merge only. A list, one entry per authorizing record.

The rule the whole change enforces: no field here may be produced by reading prose. Promotion never emits supersedes, however emphatically the content says “this replaces X”. An absent valid_from is a truthful “not stated”; a defaulted one would assert that every claim became true on its promotion date.

Where the envelope comes from

promote
stamps recorded_at; writes valid_from only if supplied
→
revise / merge
the only emitters of supersedes + revision_link
→
lint --temporal
warning-only checks on what the writers actually wrote

merge matters here: without it the envelope would have a producer and no real caller — the schema-with-no-writer failure this phase exists to avoid. A merge is a correction, so the canonical now supersedes the dup with the tombstone as its authorizing record.

Two invariants that cost the most care

recorded_at is volatile

It is excluded from the content-identity comparison, so it can never itself trigger a write. Without that, every page would differ from its own update candidate on every run — the 137-entities-churned pathology the guard was built to kill — and the field would degrade into a “last run” stamp.

Legacy pages are not backfilled

The update path cannot know when a pre-envelope page was recorded. Backfilling would not churn the graph — volatility prevents that — which is precisely what would make the mis-stamping quiet: today’s date landing on the arbitrary subset of old pages that happen to acquire an unrelated edit.

Refuse, never repair

Both correction workflows read the existing envelope before rewriting it. A value they cannot read exactly is a value they would destroy, so they refuse and leave the repair to a human.

Non-canonical entry

A bare slug or truncated wikilink is refused, not silently canonicalised.

Duplicate key

YAML keeps only the last, so a read-then-write would erase the earlier declaration.

Blank link entry

A slot somebody meant to fill — dropping it on rewrite is the same silent repair.

No frontmatter

Every setter would no-op while the command reported success.

The corollary the review forced: the audit and the writer may disagree in exactly one direction. The audit warns where the writer refuses — never the reverse. A gate that passes what the thing it gates rejects is not a gate.

Fixes landed. Scores climbed monotonically; findings narrowed from architecture to edges.

Round 4 exceeded the three-round budget deliberately. merge repointed every inbound wikilink before validating the canonical, so the abort paths round 3 had just added left third-party pages pointing at a canonical that never got merged. Shipping known corruption to satisfy a round counter is the wrong reading of the gate.

The mutation suite carries its own scar: the first “merge validates after repointing” mutation inserted a no-op instead of reordering the work, and reported a false SURVIVED. A mutation that applies but is semantically inert proves exactly as much as one that never applied.

Three findings held, not closed

Entry-to-link binding

supersedes and revision_link are parallel sets, not pairs. Round 2 stopped the data loss; what remains is expressiveness. A per-entry schema is better designed against real revisions than in advance.

Concurrent writes

Read-modify-write with no lock. Shared by promote, merge, and lint --fix; hardening one command would buy a false sense of safety.

Non-UTF-8 bytes

errors="replace" is the codebase-wide idiom. Not introduced here, and not quietly fixed in one path.

All three are written into references/temporal-revision-envelope.md § Known limitations. A limitation stated is a limitation a reader can plan around; a limitation implied away is a lie with a longer fuse.

This receipt proves parity, not precision. The new checks contribute nothing by construction, so their precision and recall on real revisions are unmeasured. Everything stays optional and warning-only; a hard gate remains blocked on that measurement plus an independent cross-review — the same bar #151 set for itself, now with two of its three conditions met and the third explicitly not.

What becomes possible next

Safe now

Record real corrections with revise. Every merge starts emitting typed provenance automatically. The audit begins accumulating a reviewed corpus of actual revisions instead of a hypothetical one.

Earn later

Calibrate supersession precision on those reviewed revisions, decide per-entry link binding against real cases, and only then discuss promoting any of it to a hard gate.
