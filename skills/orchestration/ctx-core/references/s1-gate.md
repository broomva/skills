# The System 1 injection gate, System 2 cache, and their evals

Design of record: broomva/workspace#840 §6.2 (System 1 at every hook stage,
System 2 behind it), §6.3 (claims, not paths), §6.4 (privacy and scope), §6.6
(the spike gate). Ticket BRO-2674. This file is the operating reference; the
numbers are regenerated by the commands in it.

## What runs where

| Piece | Runs | Does |
|---|---|---|
| `ctx_s2.py` (System 2) | a tick, a person, never a synchronous hook | reads the scope's items, keys them, ranks them (BM25 in v1), writes the sharded cache atomically |
| `ctx_s1.py` (System 1) | inside the hook, per event | builds keys from the payload and session state, looks them up, injects or abstains, logs the decision |
| `ctx_s1_hook.py`, `ctx-s1-hook.sh` | the registered command | flags checked in shell first; then deadline, fail-open, exit 0 |
| `ctx_s1_replay.py`, `ctx_s1_eval.py` | offline, and CI | E1 snapshot, replay and report; E3 tune; live follow-through |
| `register_s1_hooks.py` | the owner, by hand | adds or removes the stage registrations in `~/.claude/settings.json` |

## Items (System 2)

Every item is one factual line, copied from one source field, with its source
id (§6.3). The ablations found pointer lists are not read, so no item is a bare
path.

| Type | From | Claim | Keys |
|---|---|---|---|
| `spec` | `docs/specs`, `docs/plans` | title: first sentence of the lede (meta description, `.lede`, or the first non-byline paragraph) | paths, tickets, branches and PR refs it cites; words of its title, lede, headings and first 2,400 characters |
| `adr` | `docs/adrs` | the same | the same |
| `entity` | `research/entities/**` | its `core_claim` | the same, plus its wikilinks (read only by the PPR arm) |
| `memory` | the scope repos' memory dirs | `Memory rule <name> records: "<description>"`: quoted, as data | paths its body cites; words of its name, description and body |
| `pr` | open PRs and PRs updated in the last 14 days (gh, System 2 only) | `repo#n (<state> as of HH:MMZ): "<title>"` | the files it changes, its branch, its number |
| `session` | live board rows | `Session <id> is live on branch <b> in <cwd>; last event … as of HH:MMZ.` | its branch (and, in phase 2, its path claims) |

Exclusions, at the source: anything under `crm/` (and the words of a `crm/`
path in any text), a PR that touches `crm/` at all or names it in its title,
any claim or source the ctx-core guard rejects (credential-shaped), person,
persona and org entities (by directory and by type: an org entity holds facts
about people at one remove), memory files of type `user`, fork PRs
(`isCrossRepository` not false: a fork's title is anyone's text), and anything
outside the scope's own repos, memory dirs and PRs. A failed PR fetch is
counted (`pr-fetch-failed`), never read as "no PRs". Stimulus (`sri`) builds its own cache from its own repo.

## Keys (`ctx_keys.py`)

`p:` a path (repo-relative, or `~/…`), `d:` a directory of it at least two
segments deep, `f:` its last two segments, `b:` a branch, `pr:repo#n`, `t:` a
ticket, `w:` a word (lowercased, plural-stripped, stopwords out). A path whose
last segment has a file extension is a path, never a branch (`docs/specs/x.html`
vs `docs/some-spec`). Query-side only: `s:` holds the words a shell command
searches for (a grep or rg pattern, a `find -name`, a `kg load` query); its keys
are `w:` keys weighted apart.

## Scoring

BM25 per channel (each channel is a field with its own length normalisation;
keys held by more than 20% of items are dropped as naming nothing). A key's
posting is `[item, score]`, precomputed. System 1 sums a candidate's scores over
the event's keys, each times its channel weight (and an optional type weight),
in key order, so the sum does not depend on the hash seed. The sum is compared
with the stage's floor.

The ranker is a seam (`ctx_s2.Ranker`: `fit`, then `postings`). A traversal
ranker fills the same postings. `ctx_s2_ppr.PPRRanker` is the prototype: one hop
of personalized PageRank over wikilinks and item-to-item citations, seeded by
BM25, damped by in-degree^-0.5. It is an E1 arm only; `ctx-s1 build` refuses it
for the live cache. "Beats BM25" means the spec's §10 B0/B1 gates
(workspace#840 as merged), not an E1 number.

## Stages (System 1)

| Stage | Hook (matcher) | Keys | At most | Deadline inside the interpreter |
|---|---|---|---|---|
| session-start | SessionStart (startup, resume, clear) | branch | 5 claims, 1,500 chars | 300 ms |
| compact | SessionStart (compact) | the claims the session already had, re-ranked by branch | 5, 1,500; may repeat | 300 ms |
| prompt | UserPromptSubmit | prompt words (120 unique kept, `max_terms` used), tickets, PR refs, cited paths, branch | 3, 1,500 | 300 ms |
| pre-edit | PreToolUse (Edit, Write, MultiEdit, NotebookEdit) | the file's path | 2, 600; each path once; 10 a session | 70 ms |
| post-read | PostToolUse (Read, Grep, Glob) | the path read | 2, 600; each path once; 10 a session | 70 ms |
| post-bash | PostToolUse (Bash) | after `git push`: the branch; `gh pr …`: the PR; paths a plain reader reads; words it searches for | 2, 600; each path once; 10 a session | 70 ms |
| subagent | SubagentStart | only the claims the parent received, re-ranked by branch | 3, 1,000; once per subagent; none for reviewer types (`Explore` included) | 150 ms |
| post-compact | PostCompact | measurement only: which injected claims the summary kept | nothing | 150 ms |

Across stages: a claim at most once per session (compact excepted), 30 claims
per session. A session or PR claim from a cache older than 6 h or 24 h is not
offered (both carry their as-of date and time). An item whose object is the event's own file, or a file the
session already opened (the read stages record opens whatever they decide), is
never offered. Tool stages abstain inside a subagent. A subagent's claims count
against neither the parent's dedup nor its caps.

The hook stages were checked against the hooks reference and a live probe
(`s1-stage-probe.md`, CLI 2.1.280): PreCompact and PostCompact could not inject
there (the CLI rejected their `hookSpecificOutput`), so compaction re-injection runs on
SessionStart(compact); Grep, Glob and MultiEdit are not in CLI 2.1.280's tool
list, so on that CLI post-read fires on Read only.

Flags: a stage runs only when `CTX_S1=1` and it is listed in `CTX_S1_STAGES`
(csv, or `all`); `CTX_S1_SHADOW=1` logs the decision and injects nothing (spec
phase B2); a file at `~/.config/ctx/s1-off` turns every stage off. Floors come
from `references/s1-params.json`; a stage with no floor abstains on everything.

The tool stages' self-deadline (70 ms) starts once the interpreter is up, so it
does not cover start-up. Nothing bounds the wall time at 100 ms: the benchmark
(`references/s1-latency.md`) measured p99 38 to 47 ms at load average 9 to 10,
and 87 to 212 ms at 34 to 67, where process spawn alone had a p99 of 291 ms.
Workspace#840's round-7 follow-up has the wrapper timestamp interpreter start
and re-derive the budget from it: pending that spec text (macOS `/bin/sh` has
no sub-second clock, so the shell cannot stamp it without starting another
process).

## Telemetry: the decisions log

`~/.local/state/ctx/<scope>/s1-decisions.jsonl`, one line per decision, rotated
at 8 MiB. Fields: `ts`, `scope`, `stage`, `mode` (inject | shadow), `session`,
`prompt_id` / `tool_use_id` / `agent_id` when the payload has them, `path` (the
event's repo-relative path, when the guard passes it), `key_kinds` (count per
channel), `n_keys`, `top` (the five best candidates with scores, before the
floor), `floor`, `params` (version), `build` (cache build id), `outcome`
(inject | abstain | measure), `reason` (cleared-floor, no-key, no-candidate,
below-floor, no-floor, dedup, path-seen, stage-cap, session-cap, budget,
in-subagent, independent-reviewer, no-cache, state-busy, deadline), `injected`
(item ids), `bytes`, `ms`, and for post-compact `kept`. No prompt text and no
key is written; the event's own repo-relative path is (as the board keeps a
session's cwd).

Follow-through: `ctx-s1 follow` joins the log with the transcripts. A use is a
later tool call that opened the item's object (a Read or shell read of its
file, `kg load`, `gh pr view`), bstack context_ledger's definition. The claim
header `[ctx claims]` and the source ids (`research/entities/…md`,
`docs/specs/…`, `~/.claude/projects/…/memory/…md`) match the ledger's pointer
patterns; attributing the block by name needs one line in the ledger's
`KNOWN_HEADERS` (a bstack follow-up).

## E1: offline replay

```bash
S1="python3 skills/orchestration/ctx-core/scripts/ctx_s1_cli.py"   # the `ctx-s1` command (ctx.py is the core's)
D=scripts/skill_evals/ctx_s1_replay                                 # committed: aggregate reports only
$S1 -C ~/broomva snapshot --days 14                                 # -> ~/.local/state/ctx/broomva/e1/ (private)
$S1 -C ~/broomva eval --params skills/orchestration/ctx-core/references/s1-params.candidate.json --out $D
$S1 -C ~/broomva eval --params ... --ranker ppr                     # the ontology-shaped arm
```

The snapshot is derived from the owner's transcripts and is kept on their
machine, out of git: `ctx-s1 snapshot` writes it under `~/.local/state/ctx/<scope>/e1/`
(mode 0600) and refuses any directory inside a git checkout. Keys and object
ids are HMAC-SHA256-hashed under a local salt (`~/.config/ctx/s1-eval-salt`)
as a second line, not the first: each event's keys keep their order (the live
gate cuts prompt words at `max_terms` in that order), and an ordered sequence
of hashed words is open to frequency analysis, so the file is not fit to
publish. Because it stays private, it keeps what a public file could not:
event and edit times to the second, PR items, every repo's items, claim and
source lengths and each header's label length, so the replay's item set and
byte counts are the live cache's. An item whose creation is known only to the
day (a dated file name, a `created:` date) becomes a candidate 36 h after that
UTC midnight, or at its file's mtime if that is sooner, so a same-day item is
not a candidate before it was written (a backdated `created:` still can be). Only the aggregate
report (`e1-report.json`, `e1-report.md`), the tune ledger and the ranker
comparison are committed; none holds a key, a hash of one, or a per-event
record. CI replays a synthetic fixture instead (`tests/s1_synthetic.py`,
`tests/test_s1_e1_synthetic.py`): forty generated sessions where a working
gate exists, so CI checks the harness, not the owner's data.

Events are the hook events the scope's main transcripts would have fired
(subagent transcripts only through their parent). Ground truth is
counterfactual: an item was *needed* when the session first opened its object
itself. Two masks keep that from being tautological: an item any injected text
had already pointed at (a hook's output, the instruction files, MEMORY.md's
index) is never needed in that session, and an injection of it there, or one
followed by such a pointer within its window, is unjudgeable; a file the
session wrote earlier is not retrieval. An item created
after an event is not a candidate for it. A pointer counts whether it names
the item's path (in any of the scope's repos), its entity path, a memory link,
a PR (`repo#n`, a URL, a bare `#n`, the number a `gh pr` command takes), or the
item's file stem (`[[slug]]` or bare): the same recognizer as the echo check
(a partial path the gate matches by its tail is named only through its stem). A fetched path resolves to an
object exactly as the gate resolves an event's file (`ctx_s1._path_keys_for`):
a file in a nested repo of the scope is that repo's, and one in a repo outside
the scope is nothing. Each event's payload carries the session's cwd and,
for Bash, the command's output, so a relative shell read and a number-less
`gh pr view` key in the replay as they do live; after a `cd` the event belongs
to the repo (and scope) of the new cwd, as the hook resolves it. A subagent's
own fetches are masked by its prompt and by the injected text in its own
transcript, and flagged `listed` the same way.

A tool stage's claim is anchored after the assistant message that made the
call: calls issued in parallel with it were written before any hook output,
so they cannot be hits. A hit is an injected claim whose item the session then
opened first within the stage's window (10 tool calls for tool stages, 30 for a prompt, start or
compaction, 20 inside a subagent). Recall is the share of needed fetches that an
injection of the same item preceded within the window (a subagent's own needs
count toward its stage and toward all). An easy hit is one whose item the
event's own text named (echo), a tool's output had just listed (the agent, or
the subagent, read what a search printed), or whose file was edited after the
event (the replay's copy may hold keys the live gate lacked); strict precision,
strict recall and strict F0.5 leave easy hits out. Injected text that named an item first masks it: hook output, the
instruction files, MEMORY.md's index, skill bodies (meta records), @-mentioned
files, compaction file references and mid-turn queued prompts. Sessions are
split by start time: train 60% (tune fits), validation 20% (tune accepts),
test 20% (read only for the spec's bar and the report).

Arms: `gate` (the parameters), `always` (floors and caps off), `never`,
`wrong-key` (each event gets another session's keys: a mutant), and
`stage:<s>` (one stage alone) for the stages that can inject alone. compact
and subagent only re-offer claims another stage injected, so alone they never
inject: they get no one-stage arm, no tune phase and no floor until a measure
of them with another stage on exists.

The separation block is read on the TEST split, on strict hits: the gate must
inject and strictly hit, `always` must inject more, cost more and score lower
in strict precision and strict F0.5, `wrong-key` must score lower, and `never`
must inject nothing. Read on train it would pass by construction (the floors
are fitted there). It checks the harness, not the gate's worth, and on the
real snapshot it fails today: the proposal's gate makes no strict hit in 82
injections on test (`always` makes 2 in 1,765), so the replay cannot tell it
from the mutant arms there. The report prints that, and the bar per stage; no
stage clears the bar. CI's synthetic fixture is where separation is required
to pass. BM25 and System 1 run on
hashed keys exactly as on raw ones (a test pins live/replay parity), and an
item keeps only the keys some event names plus its field lengths, which leaves
BM25's scores unchanged.

## E3: the tune loop

```bash
$S1 -C ~/broomva tune --params default --trials 84 --seed 1 \
  --ledger $D/tune-ledger.jsonl --write <bar.json> --write-candidate <candidate.json>
```

One coordinate phase per stage that can inject alone (its floor, per-event cap
and budget, scored with that stage alone), then one for the channel weights
(every stage with a floor, together). The objective is strict F0.5, the metric
the bar uses: an easy hit is no gain. A proposal is accepted only when train
strict F0.5 improves on at least two strict train hits (one hit is noise to fit
a floor to), validation strict F0.5 does not fall, and bytes per session do not
grow unless strict recall does; no proposal is scored twice, and a no-op is
never proposed. Every trial goes to the ledger with its full parameters, scores
and verdict. At the end a stage keeps its floor only if, alone on the TEST
split (which no trial read), it clears the spec's bar on strict hits: precision
>= 0.30 over >= 50 injections. `--write` gets those parameters (the shipped
`s1-params.json`), `--write-candidate` the tuned floors without the bar
(`s1-params.candidate.json`, a proposal for E2 and shadow runs, fitted to a
handful of hits). The committed run starts from `--params default`
(ctx_s1.DEFAULT_PARAMS: no floor, default weights), so it owes nothing to
tuning on an earlier snapshot and reproduces from the repo. Deterministic for a
seed, bounded by `--trials`, and it only reads the snapshot. A new `ctx-s1
snapshot` replaces the private file; the committed reports and ledger name the
sha256 they came from, and a test reproduces the reports from the snapshot
where `CTX_S1_FROZEN` points at it. The test split is not read by any trial,
but its days were looked at while the harness was built (earlier rounds used
overlapping sessions as their held-out set), so it is untuned, not unseen.

A scheduled tick, when the owner wants one (not scheduled here), would run:
`ctx-s1 snapshot` weekly (private, as above); `ctx-s1 tune` on it; `ctx-s1
eval` with the result; and open a PR with the new aggregate report that
changes `s1-params.json` only when a stage clears the bar on the new snapshot
and E1's separation holds. The tick would not write the shipped parameters
itself.

## E2: behavioural ablation

`scripts/skill_evals/ctx_ablation`, task file `tasks/s1.json`: seven retrieval
tasks rewritten so the answer is a fact in one item's claim line, graded on the
concept, with no token shared between a prompt and its grader; and the two
coordination tasks as the regression guard. Arms: `bare`, `s1` (every stage),
`s1-<stage>` for each stage that can inject alone and that the proposal floors
give a floor, and `ctx` against `ctx+s1` on the coordination tasks. The retrieval tasks were written around facts the
index holds, so their lift shows that a delivered claim is used, not that the
gate picks the right claim on real traffic; E1 measures that. Every arm's case
has the same System 2 cache; only the hooks differ. Each trial records the
gate's decisions, claims, bytes and follow-through; the report adds the lift
per 1,000 injected tokens (turn-one context plus mid-turn bytes/4).

## Where this build departs from the brief, and why

- **The cache before the spike.** Spec §6.6 says no Kinetic wiring, cache or Jev
  ranking is built for B until the spike decides. What is built here is the
  spike's lexical baseline (BM25 claims, the `lex-claims` arm) and the harness
  that judges any ranker; no Kinetic and no Jev. Every stage is off by default,
  and the shipped parameters abstain on everything (§6.2's start state), so
  nothing is injected until a stage earns a floor.
- **post-bash inside the claims hook.** §6.2 runs the Bash stage inside
  ctx-core's phase-2 PostToolUse claims hook, with no second registration.
  Phase 2 is not built, so post-bash registers on its own for now;
  `ctx_s1.run_stage("post-bash", …)` is the library call the claims hook will
  make.
- **PreCompact and PostCompact** could not inject on CLI 2.1.280 (reference and probe), so they are not
  injection stages; SessionStart(compact) is, and PostCompact measures.
- **Floors from E1, not yet from live use.** §6.2 fits floors from ledger
  records (used at least 30% of the time over at least 50 injections). No live
  record exists until a stage runs, so E3 fits them on E1's counterfactual
  precision, under the same bar; `ctx-s1 follow` computes the live figure once
  stages run in shadow or on.
