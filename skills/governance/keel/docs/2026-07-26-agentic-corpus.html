The agentic corpus scored higher

Finding · 2026-07-26 · Against our own thesis

Six repositories where agents write the code were measured with the same engine, the same rubric and the same 25-node cap as the fourteen human-maintained ones. They pooled 0.947 against the published 0.853. The prediction behind "your agents are grading their own homework" is not visible in Keel's grounding ratio, and this document exists because the corpus file said it would be published either way.

The pre-registered question

If agent-maintained repositories score just as well, that is a finding against the product's own thesis and it gets published in the same voice.

What this does and does not mean

It does not mean agents are not grading their own homework. It means Keel's grounding ratio cannot see it. Those are different claims and the difference is the whole finding.

The ratio classifies the execution axis: who produces the exit code. On that axis these repositories are genuinely well wired — real test runners, real compilers, real containers, and in one case a real third-party proof-system counterparty. The number is not wrong. It is answering a question that does not discriminate.

Meanwhile, every one of the six judging passes independently reported an oracle problem in prose while assigning anchored in the verdict. Not as a caveat we asked for — as the thing each agent found most worth saying:

  • karaoke-gen — backend/tests/conftest.py replaces google.auth.default, firestore.Client and storage.Client at import and auto-overrides require_auth. The datastore, object store and auth layer the code is verified against are all repo-authored. Separately: next build does not typecheck (ignoreBuildErrors: true, no tsc --noEmit in CI).
  • kody — a repo-authored fake of the Cloudflare API is installed into both the unit suite and the preview environment, so the "external API" in those signals is code the same authors write. Production D1 backup and restore are gated on two hand-typed strings whose evidence is a prose comment — "the blocking export benchmark passed 2026-07-23" — that nothing re-executes.
  • xorq — the three strongest anchors gate no merge (workflow_dispatch only), and BigQuery pytest.skips on every credential fork, so a labelled run with an expired key goes green having executed zero BigQuery tests.
  • aspect-cli — six launcher integration tests discard the process exit status with || true and judge by grepping the binary's own debug log. Three of them have no producer outside the crate other than bash and grep.
  • wvlet — the TypeScript SDK asserts expect(sql).toContain('select name, email'). No engine ever runs the generated SQL. A committed golden file exists in highlightjs-wvlet and is read into a variable that is then never compared.

And one counterexample, which is what makes the axis real rather than rhetorical

binius64 has an oracle that is genuinely outside the write boundary: 90 proptest! blocks generating inputs nobody enumerated and asserting algebraic identities (x * x.invert() == ONE), circuit outputs cross-checked against independent implementations (sha2, sha3, blake3, k256, rsa), and a known-answer test citing RFC 6234. It scored 0.909 — lower than three repositories whose oracles are mocks.

That inversion is the finding stated as a single fact: the repository with the strongest oracle in the corpus scored below three repositories with the weakest. A metric that ranks them that way is not measuring what the product claims to measure.

What follows

U18 — the independence vector — is now supported by data rather than by argument. Its case was 68 of 122 anchored verdicts in the human corpus carrying a written admission that the oracle or the scope sat inside the boundary. That was an argument from prose. This is the same finding as a measurement: two populations, an execution-axis ratio that separates them by less than its own sampling noise, and an oracle axis that visibly separates them in the transcripts and is counted nowhere.

The schema change it needs — writeBoundary.independence: { execution, oracle, scope }, each failing closed — is a re-freeze decision, and the argument for spending it is now empirical.

The non-coverage finding landed too, exactly where it was aimed. aspect-cli was chosen for its CI shape: Buildkite, CircleCI, GitLab, twelve GitHub workflows and Bazel. Keel reads three of those five. .buildkite/pipeline.yaml holds bazelrc-e2e, a gate that exists nowhere else by explicit design — the repo's own comment reads "intentionally NOT ported here… It stays a Buildkite-only test on main." A load-bearing gate that structurally cannot appear in any ratio Keel computes for that repository.

Follow-up filed: corpus.ts does not carry gather's unread-surface record into the report, so the blindness disclosure shipped in #18 does not reach corpus artifacts — the one place this run proves it was needed.

Limits, before anyone quotes the number

  • Six targets, 25 nodes each. Every judging pass volunteered that its ratio was sample-shaped: karaoke-gen's draw landed on eight package.json scripts, aspect-cli's never touched ci-workflows.yaml, the 25-job workflow that is the actual PR gate. A denominator of ten to seventeen does not support decimals.
  • The predicate measures surviving trailers, not agent authorship. Squash merges drop commit bodies, so openai/codex and sst/opencode both measure 0.000. This corpus is therefore biased toward solo-maintainer and small-org repositories and away from large organisations with merge hygiene. 93 repositories were cloned to assemble six.
  • Five of six are Claude-trailered. kody was the only non-Claude agent-authored repository found at scale, and that scarcity is itself a limit on what can be concluded.
  • Agent tooling was excluded deliberately — several qualified at higher rates. A finding drawn from repositories built to serve agents would be attackable as being about their CI conventions rather than about agent-written code.

Keel measures the shape of verification, not its quality. A repo can be 100% anchored with terrible tests. This corpus is six repositories that are largely well-wired on the axis Keel measures, and the reason that is worth publishing is that it was supposed to come out the other way.
